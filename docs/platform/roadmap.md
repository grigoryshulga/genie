# Дорожная карта genie-платформы

Видение — [[platform/vision]], решения — [[platform/decisions]], бэкенд — [[platform/backend]], знания — [[platform/knowledge-vault]], автоматизации — [[platform/automations]].

Принципы нарезки:

- каждая фаза заканчивается проверяемым результатом;
- порядок задают зависимости, а не сроки: срока у 1.0 нет;
- совместимость данных и API можно ломать, пока у genie нет других пользователей (миграцию своей базы делаем);
- ниже сначала то, что сделано (история), потом путь к 1.0.

## Git-хостинг (Ф6, 2026-09-29)

Сделано: несколько репозиториев на проект с путями, GitHub, GitLab (в том числе self-hosted) и «plain»-серверы, политика доступа и слияния, прокси для агентов без учётных данных хостинга, PR/MR и слияние через сервер, наблюдатель CI и слияний, ворота `review`/`done`, события `git.*`/`cr.*`/`ci.*`, веб и CLI администратора — [[platform/git-repositories]]. Осталось из Ф6: webhooks вместо опроса (нужен публичный адрес), GitHub App, форки, LFS.

## Готовность к пилоту (2026-09-29)

Для пилота с командой добавлены: песочница агентов (bubblewrap), автономность `assisted` и интеграция по умолчанию у проекта, люди в задачах (ответственный, упоминания, «Мои задачи»), веб для администраторов (проект, люди, приглашения, сервер), `genie doctor`, systemd-юниты и ротация копий, синхронизация базы знаний с git для Obsidian у каждого, `genie stats`; с 2026-09-29 — каталог операций: всё, что есть в вебе, — и в командной строке `genie <объект> <действие>` для людей, скриптов и агентов (таблица команд в промпте строится из него же), MCP-сервер `/mcp` для своих агентов людей и пульт оркестратора `genie orchestrate` (ваша сессия pi — оркестратор проекта, серверный ждёт). Как провести пилот — [[platform/pilot]]; решения по умолчанию — [[platform/decisions#Применено для пилота (без отдельного подтверждения)]].

## 1.0

**Версия 1.0 — команда живёт в genie каждый день.** Люди сами ведут работу через менеджера проекта и оркестраторов, а не чинят genie. Устойчивость и польза в повседневной работе важнее ширины. Срока нет, порядок задают зависимости. Совместимость можно ломать.

Поэтому оркестрацию можно перестраивать заново, но до этого нужен короткий пилот на текущей модели: его наблюдения становятся требованиями к менеджеру и оркестраторам эпиков.

### Фаза 0. Пилотный мост

Эпик «Пилот: надёжный рантайм и общий сервер». Цель — устойчивый рантайм и короткий пилот на чужом проекте на текущей оркестрации.

- Гигиена: уборка веток и worktree, этот документ.
- Надёжность: баг команды без шаблона, восстановление после падения с настоящим pi, сторож зависших агентов, бюджеты, тесты песочницы, нагрузка, разбивка больших модулей, восстановление из резервной копии.
- Малая часть №4: лимит работы, который не даёт задачам идти потоком.
- №10: ожидание CI перед закрытием задачи и повторы проверок.
- Разведка №8: формат окружения проекта (`devcontainer.json`, Dockerfile на проект или Nix) и его влияние на песочницу. Нужна до выбора проекта для пилота: сборка чужого кода упирается в тулчейн хоста.
- Проверка общего сервера на двух машинах.
- Пилот: 5–10 задач на проекте команды, журнал наблюдений, пересмотр этого плана.

Готово, когда: рантайм переживает падения без потерь почты и сирот, пилот прошёл, наблюдения записаны.

### Фаза 1. Менеджер проекта и память

Идеи 2 и 3. Начинаем с дизайн-заметки про память: что хранит менеджер (договорённости с владельцем, предпочтения, отложенное, уже опробованное), где (раздел vault, таблица или сжатие диалогов), как забывает. Эта же память нужна оркестраторам эпиков, поэтому проектируем её один раз.

- Роль «менеджер проекта»: один на проект, долгоживущий.
- Чат с менеджером: завести задачу, обсудить план. Обобщает разбор идеи с планировщиком.

Готово, когда: через чат с менеджером можно спланировать и завести работу, а менеджер помнит решения между сессиями.

### Фаза 2. Оркестраторы эпиков и планирование

Идеи 1 и 4. Строится на памяти из фазы 1. Нельзя вести параллельно с фазой 1: обе зависят от одной модели «кто кому пишет».

- Оркестратор на эпик: своя сессия, спит и просыпается, память — артефакты эпика и общая память.
- Планирование: очередь и приоритеты, окна работы, лимиты, бюджеты; работа выпускается явным решением менеджера или человека.

Готово, когда: два эпика идут параллельно со своими оркестраторами, а поток задач ограничен явным планом.

### Фаза 3. Рутины

Идея 5. Опирается на автоматизации и на менеджера (кому приходят сводки).

- Коннекторы: Sentry, логи, алерты (через шлюз MCP).
- Дайджесты и утренние сводки в Telegram и почту.
- Шаг «из находки сделать задачу».
- Уборка документации по расписанию.

### Фаза 4. Командная работа и окружение

- №6: ревьюер предлагает патч (режим «предлагает»), решение о режиме «коммитит» принимаем осознанно: независимость ревьюера под вопросом.
- №9: личные входы в провайдеров, не только LiteLLM; кто платит за агента.
- №7: сначала навигация для агентов (L0/L1, impact), потом форматы файлов и HTML-страницы.
- №8: реализация выбранного формата окружения, зависимости проекта, контейнер на команду.

Вебхуки вместо опроса, входящая почта (IMAP), dry-run автоматизаций, настройки уведомлений и тихие часы, GitHub App, форки и LFS, английская документация, облако компании (SSO, Postgres).
