# Решения по платформе genie

Видение — [[platform/vision]], план — [[platform/roadmap]].

## Принятые владельцем (2026-09-28)

| № | Вопрос | Решение | Что это меняет в плане |
|---|---|---|---|
| PD1 | Модель поставки | Одна инсталляция на команду, без мультиарендности | Нет изоляции арендаторов и биллинга; одна БД сервера на команду |
| PD2 | Развёртывание | На время тестирования всё разворачивается на локальной машине; контейнеризация и облако компании — отдельный этап | MVP — бинарь сервера и pi на localhost; в MVP только каналы, которым не нужен публичный адрес; контейнеры — Ф7 |
| PD3 | Где хранить знания | Не в репозитории кода: Obsidian-подобное хранилище, как минимум отдельный репозиторий | Vault — отдельный git-репозиторий, совместимый с Obsidian ([[platform/knowledge-vault]]) |
| PD4 | Публикация документации агентами | По политике раздела | Политики `direct` / `review` / `locked`, отдельно для людей и для агентов |
| PD5 | Каналы MVP | Telegram и почта | Slack, Mattermost и другие — позже, через исходящие webhooks |
| PD6 | Проекты без кода | Поддерживаются с первой версии | Тип проекта без репозитория; команды без worktree; результат — артефакты и страницы vault |
| PD7 | Лимиты расходов на модели | Пересмотрено 2026-10-03: genie считает расходы (`modelPrices`, таблица `usage`) и останавливает команды по бюджетам задачи, эпика и суток (G-81); лимиты провайдера остаются внешним ограничением | Видно, во что обходится работа, и поток задач не съедает деньги незаметно; бюджет на человека — [[platform/proposals#Фаза 4]] |
| PD8 | Язык бэкенда | Rust | Сервер и CLI — Cargo-workspace в этом репозитории ([[platform/backend]]); Go рассматривался как альтернатива |
| PD9 | Подключение через pi и других агентов | Нужно; интеграции прорабатываются отдельно | Агентский контракт (MCP + HTTP) закладывается в Ф1, адаптеры харнессов — отдельный трек |
| PD10 | Порядок работ | Сначала перенос ядра на Rust; новые возможности пишутся сразу на Rust | TS-версия остаётся рабочей до переключения (конец Ф1), на TS — только исправления |
| PD11 | Репозиторий | Пока монорепозиторий: Rust-сервер, SPA, расширение pi, промпты ролей | Один релиз, общие контракты и тесты; вопрос можно пересмотреть позже |
| PD12 | Общение агентов (2026-09-28) | Процесс pi на агента; прерывают только оркестратор и люди; простаивающая сессия останавливается через 15 минут; вопрос тиммейту ждёт ответа до 3 минут | Живые сессии pi в режиме RPC с доставкой почты между шагами ([[platform/agent-bus]]); заменяет запуск «ходами» (PP9) для команд и оркестратора |
| PD13 | Где живёт настройка ролей и команд | В конфигурации сервера: genie поставляется с ролями и пресетами команд по умолчанию, администратор настраивает их под свой контекст — навыки, MCP-серверы, разрешения | Роли — `<data>/agents/<id>.md`, шаблоны — `<data>/teams/<id>.json`, навыки — `<data>/skills/`, MCP — `<data>/mcp.json`; веб правит те же файлы; роль или шаблон под проект — поле `projects` ([[platform/agent-roles-and-teams]]) |
| PD14 | Кто правит роли, шаблоны, навыки и MCP | Только администраторы сервера | Остальные видят каталог и пользуются шаблонами в задачах и автоматизациях |
| PD15 | Модель ролей | Класс процесса плюс настройка разрешений | Статусы и шаги оркестратора остаются зашитыми; роль правит набор класса через `allow` и `deny` |
| PD16 | Доступ ролей к MCP | Пока — MCP-конфиг харнессу при старте агента | Фильтр в защитном расширении pi; шлюз MCP в genie — позже. Шлюз сделан (Р5, [[platform/agent-roles-and-teams]]): по умолчанию агенты ходят в MCP через сервер, секреты остаются на сервере, вызовы — в журнале; `"gateway": false` оставляет прежний способ |
| PD17 | Режим «оркестратор — ваша сессия pi» (2026-09-29) | Сохраняется, но как клиент сервера через MCP-сервер genie | `genie orchestrate`: сессия берёт пульт оркестратора проекта, серверный оркестратор ждёт; TS-расширение с ядром уходит ([[platform/backend#Уход от TS-ядра]]); сделано 2026-09-29 — инструменты сессии через командную строку `genie` с токеном пульта, MCP-сервер — для остальных агентов людей |
| PD18 | CLI (2026-09-29) | Полный паритет для агентов и управления сервисом через агента | MCP и CLI — два входа в один каталог операций; паритет проверяет тест |
| PD19 | Контекст знаний для агентов (2026-09-29) | Переносится в Rust: L0 — перечень страниц в системном промпте, L1 — подборка страниц к старту задачи | Спецификация — тесты `src/docs/context.ts` |

## Репозитории проектов и git (2026-09-29)

Подробности и «почему» — [[platform/git-repositories]].

| № | Вопрос | Решение | Что это меняет |
|---|---|---|---|
| GR1 | Аутентификация к хостингам | Токен бот-учётки (или group/project access token); GitHub App и короткоживущие токены — позже | Секрет — токен репозитория проекта (см. GR1a), в `git.json` секретов нет; права токена — второй рубеж защиты |
| GR1a | Токен на репозиторий (2026-10-01) | Токен (PAT) задаёт администратор проекта у самого репозитория; токенов хостинга в `git.json` больше нет (`token`/`token_file` отклоняются с подсказкой) | Токен лежит в `server.db` зашифрованным (тот же механизм и ключ `secrets.key`, что у ключей LiteLLM), привязан к проекту и репозиторию, не показывается и не передаётся агентам; в CLI — только со stdin |
| GR2 | Как агенты ходят на хостинг | Никак: у них нет учётных данных; `origin` их клона — прокси сервера, который проверяет каждый push по политике | Правило «только PR/MR» держит сервер, а не промпт или запрет команд |
| GR3 | Кто сливает по умолчанию | Человек; `agent_after_approval` и `auto` включаются политикой репозитория | Задача с открытым запросом не закрывается, пока запрос не слит |
| GR4 | Какие репозитории видит задача | Читает — все, что разрешают роль и политика; пишет — только названные в задаче | Проект с несколькими репозиториями просит назвать их до запуска команды |
| GR5 | Репозиторий в нескольких проектах | Разрешён: общее зеркало, раздельные политики и рабочие копии | Хранение по хостингу и пути, а не по проекту |
| GR6 | Права роли на git | Поле `git: none\|read\|write` в файле роли, по образцу `mcp` (PD13); слои только сужают | Ревьюер с `files: read` не запишет, что бы ни разрешила политика |
| GR7 | Привязка к конкретному хостингу | Нет: общее решение (`github`, `gitlab` в том числе self-hosted, `plain`); ориентир — GitLab 19.2.6, HTTPS и SSH | Особенности инсталляции — настройки `git.json` (CA, прокси, `api_url`, шаблоны адресов, SSH) |

## Применено для пилота (без отдельного подтверждения)

Решения по умолчанию, принятые при подготовке к пилоту (2026-09-29); каждое можно пересмотреть — они меняются настройкой, а не кодом, если не сказано иначе.

| № | Вопрос | Как сделано | Почему |
|---|---|---|---|
| PP11 | Изоляция агентов до контейнеров | Песочница bubblewrap на каждого агента (`runtime.sandbox`, по умолчанию `auto`): система только для чтения, запись — в свой рабочий каталог и его репозиторий, данные сервера, чужие проекты и ключи из домашнего каталога скрыты | Секреты каналов и чужие проекты недоступны агентам без контейнеров и без root; частично закрывает RQ6 |
| PP12 | Кто закрывает задачи в пилоте | Рекомендуемая автономность — `assisted`: оркестратор ведёт задачи, закрывают люди (сервер не даёт оркестратору `done`/`cancelled`) | Люди видят каждый результат, пока не накопилось доверие |
| PP13 | Интеграция результата | Интеграция по умолчанию — настройка проекта, команда получает её с задачей | Не договариваться заново в каждой задаче |
| PP14 | Человек в задаче | Отдельное поле «ответственный» (логин участника проекта) рядом с командой агентов; вопросы агентов — ответственному и автору; `@login` в комментарии уведомляет | Агенты знают, кого спрашивать; у человека — «Мои задачи» |
| PP15 | Пересечение правок базы знаний | Синхронизация с git каждые 2 минуты; где одни и те же строки изменили в двух местах, на странице остаётся версия сервера, версия из репозитория ложится рядом (`.conflict`), владельцы раздела и администраторы получают уведомление | Ничего не теряется, работа не останавливается |
| PP16 | Эксплуатация | systemd-служба от отдельного пользователя, ежедневная копия с хранением 14 штук (включая конфигурацию с секретами, права 0700), `genie doctor` перед запуском | Минимум ручной работы у владельца пилота |
| PP17 | Описания ролей и шаблонов | Описания встроенных ролей и шаблонов — по-русски (их читают и люди в вебе, и оркестратор); промпты и заметки связей остаются на английском | Интерфейс для людей — на их языке |
| PP18 | Метрики пилота | `genie stats` и вкладка «Статистика» на странице «Сервер» (с графиками по дням): задачи, время до готовности, вопросы агентов и скорость ответа, возвраты с ревью, сбои запусков; критерии успеха — в [[platform/pilot]] | Пилот оценивается цифрами, а не впечатлением |

## Разобрано и отложено

### pi-durable вместо `pi --mode rpc` (прототип `proto/durable`, 2026-10-03)

Вопрос: может ли `@earendil-works/pi-durable` заменить запуск pi на каждый ход (`sessions.rs` + `genie-bus.ts`). Проверено на поддельной модели (`node main.ts`, без настоящих провайдеров и Rust-моста):

- **почта**: дедупликация по `requestId`, отзыв и отказ-при-занятости работают; steer попадает после следующего раунда инструментов, а не перед каждым запросом (нужен был бы хук `beforeRequest`); уровни срочности остаются в шине genie.
- **падения**: SIGKILL посреди инструмента, повторное открытие SQLite — тот же `requestId` возвращает отвеченную отправку, инструмент не повторяется, модель узнаёт о прерывании; карта агент → conversationId должна жить в базе genie.
- **песочница**: шелл идёт через bwrap (`shellPath`), но чтение/запись/правка файлов выполняются в процессе харнесса — их охраняет только наивная проверка путей (симлинки не проверяются). Слабее сегодняшнего, где весь pi целиком в bwrap.

Вывод: модель подходит, мигрировать рано — API экспериментальный (0.99 → 1.0.1), рантайм на TypeScript (нужен Node-сайдкар и мост, не проверено), песочница слабее, шина остаётся в Rust. Вернуться, когда API устоится. Что стоит взять уже сейчас: `replay: "safe"` для инструментов, мемо эффектов, намерение записывается до действия.

Не проверено: настоящие провайдеры `/login` и прокси, навыки, AGENTS.md, MCP, codemode, нагрузка. Ветка сохранена тегом `archive/proto-durable`.
